## Correction de reprise

Les trois scripts declaraient la meme queue avec des cles de dead-letter
incompatibles : telemetry.dlq, dead, failed. La configuration partagee retient
failed, deja utilisee par le dernier preflight. RabbitMQ ne migre pas les arguments
d'une queue existante : en cas de conflit, inspecter avant toute intervention.
Aucune suppression automatique n'est ajoutee.

L'ancienne entree step10e-rabbitmq-b1.ts est desactivee avant tout acces reseau :
elle purgeait les deux queues et appelait commits un ensemble en memoire.
Le preflight et le normal-path utilisent maintenant la meme configuration et
refusent les endpoints RabbitMQ non locaux. Le preflight ne publie aucun message
et ne lit ni ne modifie PostgreSQL.

## Prochaine action

Depuis la racine applicative, Docker/RabbitMQ actif :

```powershell
npx tsx scripts/benchmark/step10e-rabbitmq-b1-topology.ts
```

Attendu : status ok, queueType quorum, mainDepth 0, dlqDepth 0.
Un status ok signifie uniquement que la topologie a pu etre declaree.
Un canal confirm cree ne prouve pas encore la confirmation de messages.
Des profondeurs non nulles doivent etre inspectees, jamais purgees aveuglement.

## Avant d'executer le normal-path

Le script normal-path reste experimental et n'est pas valide par cette correction.
Revoir avant execution :
- cible PostgreSQL isolee persistante entre crash/restart, sans nettoyer une
  table metier partagee par un marqueur global ;
- type vehicle_id conforme aux UUID des vehicules (conversion Number a retirer) ;
- attente de toutes les operations en cours avant nettoyage ;
- timeout annule, erreurs de canal et messages mandatory retournes geres ;
- verification des identites exactes et des doublons, pas seulement des compteurs ;
- unackedDepth mesure ou explicitement inconnu, jamais code en dur ;
- retries, delais et limite de livraison verifies sur la version du broker :
  x-delivery-limit ne doit pas etre assimile sans test a trois tentatives applicatives.

Les six scenarios restent : normal ; crash avant commit ; crash apres commit
avant ACK ; panne DB ; message invalide vers DLQ ; redemarrage broker.
